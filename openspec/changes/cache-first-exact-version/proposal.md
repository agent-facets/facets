## Why

`facet add <name>@<exact-version>` (e.g. `facet add cowsay@0.0.1`) contacts the registry even when the exact content is already in the local cache — observed ~1.45s with a warm cache and a hard failure when the registry is unreachable, versus ~0.10s for a cache hit. The root cause is architectural: `facet add` and `facet remove` both **write `facets.json` first**, then invoke the shared install pipeline, which reads that mutated manifest back as its source of truth. By the time resolution runs, an explicit `add` request is indistinguishable from a plain `install`, so the cache lookup is gated on a satisfying lockfile entry — a fresh add has none, so it always fetches.

This conflation also makes a `latest`/wildcard `add` behave like reproduction (honoring the lockfile) when the user is explicitly asking for the newest version. The fix is to split the work into a **plan** phase (decide what is changing) and a **commit** phase (resolve, materialize, and write), and to feed commit an explicit delta instead of a pre-mutated manifest.

## What Changes

- **Distinct network operations, named and gated independently.** *Version resolution* asks the registry what exact version a specifier means; it is needed only when no exact version is already known. *Archive resolution* downloads the bytes for an exact `name@version`; it is needed only on a cache miss. A warm cache skips archive resolution regardless of how the version was determined — this is what fixes the original bug. A third, *integrity confirmation*, gates lockfile-entry creation (see the integrity bullet).
- **Plan is pure routing — no network, no lockfile, no cache, no resolution.** Plan turns a request into a delta: `additions` (each carrying the user's specifier **verbatim** — exact, `0.*`, `*`, `latest`, or bare) and `removals` (names). `facet install` carries no request and produces an empty delta. All resolution moves to commit.
- **Commit owns all resolution, keyed on a structural discriminator.** Whether the lockfile is trusted depends on where an entry comes from:
  - **In `additions`** (an explicit request) → the lockfile is NOT trusted. An exact specifier needs no version resolution; any non-exact specifier ALWAYS triggers version resolution (newest / newest-in-range), even when the lockfile already satisfies it.
  - **From the manifest, not in additions** (reproduction) → the lockfile IS trusted. A satisfying recorded version needs no version resolution; only an **absent** entry (no lockfile entry) or a **stale** entry (recorded version no longer satisfies a changed specifier) triggers it.
  - In all cases, once an exact version is in hand, the cache is checked first and archive resolution happens only on a miss.
- **Manifest-write policy lives in commit.** A bare add is **pinned** to the resolved exact version in `facets.json`; an explicit specifier (`1.2.3`, `0.*`, `*`, `latest`) is written **verbatim** and floats. The lockfile always records the resolved exact version.
- **Commit accepts a delta and writes both files transactionally.** Commit takes the on-disk `facets.json` plus in-memory `additions`/`removals`, merges in memory, materializes, and writes `facets.json` and `facets.lock` **together** under the existing journal so any failure rolls back both. The write-ahead snapshot/restore and post-install pin rewrite in `facet add` and `facet remove` are removed; add, remove, and install become one commit path differing only by delta.
- **Integrity stays entirely in commit — a cache hit is never taken on trust.** The planner never sees integrity. Downloads are verified as before (registry checks, plus the recorded lockfile integrity when the project pins that version), then cached. Cache hits are re-verified against the integrity recorded at cache time; tampered content is evicted and re-fetched. Content is then anchored: against the locked integrity when pinned, or — when a new lockfile entry is being created — against the registry's published integrity (*integrity confirmation*: a metadata request, never a download, and an offline failure rather than an unconfirmed entry). Reproducing an already-locked entry stays fully offline-capable.
- **Frozen lockfile is a commit gate.** A frozen commit with a non-empty delta is rejected immediately (so `add`/`remove` can never run frozen). Version resolution is forbidden (an absent or stale entry fails immediately); integrity confirmation never fires (frozen never creates lockfile entries); archive resolution is allowed (a cold-cache frozen install downloads the locked versions). Every facet — cached or downloaded — must reproduce its locked integrity before materialization. Receipt-driven drift removal still runs and rewrites the receipt; the lockfile and manifest are never written.
- **Machine-local install record.** Introduce a not-version-controlled, per-project record of what *this machine* has materialized, separate from the lockfile — keyed by the project's canonical location and self-identifying (a mismatched or corrupted record fails closed and is rebuilt, never acted on). Drift removal compares the desired set against this record — not the on-disk lockfile — so a `git pull` that drops a lockfile entry no longer orphans assets: the record still describes them and removal cleans them up **offline** (no cache, no network), deleting recorded paths only when they resolve inside the project's adapter trees. The record is written transactionally with the manifest and lockfile, and bootstraps from the lockfile on first operation.
- **BREAKING (internal only):** the install pipeline's entry contract changes from "read the already-written manifest" to "apply an explicit additions/removals delta." This is an engine-internal API; there is no published surface change.

## Non-Goals

- **Per-adapter materialization tracking.** The receipt is adapter-agnostic. Install and removal run idempotently across the currently-selected adapter set and converge, so cleaning up assets left behind when a user *removes an adapter* is out of scope here (it is an adapter-management concern).
- **Recovering already-orphaned assets.** Migration bootstraps the receipt from the current lockfile, which records what *should* be on disk. Assets orphaned by a pull that happened *before* this change shipped cannot be retroactively detected.

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `installation`: Distinguish **explicit requests** (entries the user adds) from **reproduction** (entries already recorded in the manifest), with the lockfile trusted only for the latter. Specify that a non-exact add always resolves the newest matching version over the network while a satisfying reproduction entry does not, and that the cache is consulted by fully-qualified version (not gated on a lockfile entry) so an exact add is served from a warm cache with no network. Specify the manifest-write policy (bare add pins to exact; explicit specifiers persist verbatim). Specify that the manifest and lockfile are written together as one transactional commit so a failed add or remove leaves both files unchanged. Refine the frozen-lockfile requirement so its prohibition is expressed as "no version resolution" (archive resolution remains allowed).

## Impact

- **Code**:
  - `packages/engine/src/install/run-install.ts` (the commit phase) — accept `additions`/`removals` inputs; merge the delta in memory; own all version/archive resolution; key cache-first materialization on the fully-qualified version (not on `effectiveLocked`); drive drift removal from the **receipt** rather than the on-disk lockfile; write `facets.json`, `facets.lock`, and the receipt together under the existing journal/rollback.
  - `packages/engine/src/install/plan-facet.ts` (and the plan entry point) — planning becomes pure routing: emit the user's specifier verbatim as additions and names as removals; no network, lockfile, cache, or resolution.
  - A new module under `packages/engine/src/install/` — read/write the machine-local install record, and bootstrap it from the lockfile when absent. (Where the record lives on disk and how projects are keyed within it is a design decision.)
  - `packages/engine/src/install/run-add.ts` / `run-remove.ts` — stop writing `facets.json` ahead of install; drop the snapshot/restore and the post-install pin rewrite; pass a delta into the commit phase.
  - Registry prerequisite (facet-cafe): **already satisfied** — the deployed API publishes `content_integrity` in version metadata, and the contract is synced into this repo's OpenAPI snapshot.
- **Tests**: fresh exact add with a warm cache and no lockfile entry — no content download, registry integrity confirmation required, fails offline; exact add of an already-locked version succeeds offline against the locked integrity; tampered cache content is evicted and re-fetched, never installed; `latest`/global-`*`/bare add hits the network even when cached and fails offline; bounded-wildcard add re-resolves even when the lockfile satisfies; reproduction of a satisfying entry skips version resolution but downloads on a cache miss; add/remove failures leave all three files unchanged; orphan-on-pull removes assets offline via the receipt (also under `--frozen-lockfile`, updating the receipt but never the lockfile); a receipt path escaping the adapter trees is reported, not deleted; removal succeeds with no network and no cache.
