facet — authoring instructions for AI agents

Authoring a facet means writing or changing its facet.json manifest and its
asset files. The loop is: scaffold → change → verify. You can do all of it
non-interactively. Do NOT use `facet edit` (it is an interactive TTY wizard);
use `facet modify` or edit files directly, then verify.

Asset file layout (relative to the facet root)
  skills/<name>/SKILL.md    A skill (may ship companion files beside it).
  agents/<name>.md          An agent.
  commands/<name>.md         A command.
Asset names are a single segment: 1-64 chars, lowercase letters/digits/hyphens,
no leading/trailing/consecutive hyphens, and no slashes. A skill and a command
must NOT share a name (agents are a separate namespace).

The name you declare is the AUTHORED name. It fixes the asset's archive paths
and every integrity hash, and it is what facets.lock records. A consuming
project may install the asset under a different name, or omit it entirely, if
it collides with another facet — so do not assume your names land verbatim on
a user's disk. Nothing about authoring changes because of this; pick names that
are unlikely to collide (a distinctive prefix helps) and you make it a non-issue
for your users.

1) SCAFFOLD a new facet — `facet create`
   Pass headless flags to skip the interactive wizard:
     facet create ./my-facet \
       --name my-facet \
       --description "What it does" \
       --version 0.1.0 \
       --skill greet --agent helper --command run
   Repeat --skill / --agent / --command for multiple assets. Use --private to
   mark the facet private, --force to overwrite an existing facet.json, and
   --json for structured output. At least one asset is required.
   By default `facet create` also writes and declares an editable README.md
   (seeded from the name and description). Pass --no-readme to skip it.

2) CHANGE an existing facet — `facet modify`
   Grammar: facet modify <target> <name> [directory] [flags]
   <target> is skill | agent | command | facet. [directory] defaults to the
   current directory and must contain a facet.json.

   Add an asset (creates the manifest entry AND scaffolds the file):
     facet modify skill greet --add --description "Greets the user"
   Change an asset's description:
     facet modify agent helper --description "Reviews code"
   Rename an asset (moves its file too):
     facet modify command run --rename start
   Remove an asset (deletes its file too):
     facet modify skill greet --remove
   Set facet-level metadata (target is the literal word `facet`):
     facet modify facet --version 1.0.0 --description "..." --private

   Rules:
   - Exactly one lifecycle action per call: --add, --remove, or --rename.
   - --description and adapter flags may accompany --add or --rename, or stand
     alone. --remove takes no other field flags.
   - Add --json for a structured change summary.
   - `facet modify` manages asset primaries only. It does NOT manage
     supplementary files (README.md, LICENSE, skill companions) — handle those
     by editing facet.json directly (see step 3).

3) SUPPLEMENTARY FILES — README.md and other non-asset files
   A facet may ship non-asset files that are integrity-protected but are not
   installable assets. They are declared as EXACT paths (no globs). There are
   two declaration sites:
   - Top-level `files` (an array on the manifest): repo-relative paths like
     README.md or LICENSE. These ship in the archive but are NEVER written to
     disk at install time (archive-only).
   - A skill descriptor's `files` (an array on that skill): paths relative to
     the skill directory. These are companions — they materialize and are
     removed atomically with their owning skill. A companion cannot be
     SKILL.md itself. A top-level path must NOT resolve under skills/.

   To add or manage a README on an EXISTING facet, non-interactively:
     1. Write or edit the file (e.g. README.md) at the facet root.
     2. Declare its exact path in the manifest's top-level `files` array, e.g.
          "files": ["README.md"]
     3. Verify: facet build --verify
   Both README.md and the extensionless README are ordinary top-level `files`
   entries — there is no README-specific manifest field.

3b) MCP SERVERS — declaring a server a facet expects
   A facet may declare MCP servers in a top-level `servers` map. `facet modify`
   does NOT manage servers; edit facet.json directly.

   A declaration is portable CONNECTION INFORMATION, not a package reference.
   It is exactly one of two closed shapes:
     "servers": {
       "filesystem": {
         "type": "stdio",
         "command": "npx",
         "args": ["-y", "@modelcontextprotocol/server-filesystem", "."],
         "env": { "LOG_LEVEL": "info" }
       },
       "docs": { "type": "http", "url": "https://mcp.example.com/docs" }
     }

   Rules:
   - `type` is required and selects the shape. Never mix fields across shapes
     (no `url` on stdio, no `command` on http).
   - `command` must be non-empty. `args` order is significant and preserved.
   - `url` must be an absolute http: or https: URL.
   - `env` names must match [A-Za-z_][A-Za-z0-9_]*; values are LITERAL strings
     with no substitution.
   - Server names use the asset-name grammar and live in their own namespace,
     so a server and a skill may share a name.
   - Declaration objects are CLOSED: any member outside the selected shape
     (headers, cwd, shell, ...) is REJECTED. This is a deliberate exception to
     the manifest's tolerate-unknown-fields rule, because these fields change
     what executes.
   - Older speculative forms — a version string, or { "image": ... } — are
     rejected outright in every manifest format.

   A facet may declare ONLY servers and no assets; that is a valid facet.

   NEVER put a secret, token, or credential in `env`. Those values ship inside
   the published archive in plain text. Authentication is the consuming tool's
   job. Building never launches or contacts a declared server.

4) ADAPTER CONFIG — per-asset, per-adapter settings
   Each skill/agent/command may carry an `adapters` block in facet.json: a map
   of adapter name to a free-form config object that the CLI passes through to
   that adapter at install time. Set it with a name-embedded flag whose value
   is a JSON object (the whole suffix after `--adapter-` is the adapter name,
   so hyphenated names like claude-code work):
     facet modify skill greet \
       --adapter-claude-code '{"permission":{"bash":"ask"}}' \
       --adapter-opencode    '{"model":"..."}'
   Setting an adapter REPLACES that adapter's block wholesale. Remove one with:
     facet modify skill greet --remove-adapter-opencode

   Equivalent hand-edit: you may edit facet.json directly instead. Add an
   `adapters` object to the asset's descriptor, e.g.
     "skills": {
       "greet": {
         "description": "...",
         "adapters": { "claude-code": { "permission": { "bash": "ask" } } }
       }
     }
   Hand-edits round-trip safely; the CLI preserves unknown descriptor fields.

5) VERIFY — always validate after changes
   Run the full build pipeline WITHOUT writing any output:
     facet build --verify
   Add --json for a machine-readable result (ok, errors, warnings). A clean
   verify means facet.json and all asset files are valid and buildable. To
   produce the actual .facet artifact, run `facet build` (no --verify).
