## Usage

```sh
facet install
```

Reads `facets.json`, fetches and materializes every facet declared there, and writes a `facets.lock` recording the exact resolved versions and integrity hashes. Used after a fresh `git clone`, after pulling teammate changes that updated the manifest, or to reapply assets after manual edits to adapter directories.

`facet install` does not accept positional arguments  -- to add a new facet, use [`facet add`](/cli/add).

## Flags

<ResponseField name="--verbose" type="boolean">
  Show detailed step output on stderr. Verbose output never reproduces an MCP server declaration — see [Where declarations appear](#where-declarations-appear).
</ResponseField>

<ResponseField name="--accept-mcp" type="boolean">
  Approve the MCP server configuration this operation would write, without prompting.

  This is the **only** non-interactive way to accept MCP configuration; there is no second override flag. It approves the complete set the operation would write — declarations and [native takeovers](#taking-over-an-existing-entry) alike — exactly as pressing *Approve all* on the interactive screen does.

  Passing it in an interactive terminal skips the approval screen rather than pre-selecting an answer on it. Frozen mode never prompts but does honor this flag.

  It does **not** authorize an [asset takeover](#taking-over-an-existing-file) or resolve an asset [name collision](#name-collisions). Those are separate questions about different state.
</ResponseField>

<ResponseField name="--frozen-lockfile" type="boolean">
  Treat the lockfile as the source of truth; fail on any manifest/lockfile drift.

  Setting this flag makes the **lockfile authoritative**: no re-resolution, no lockfile writes, and every facet — including local sources — must reproduce its locked integrity. It also requires the lockfile's recorded [materialization](/specification/materialization) intent to match `facets.json` exactly. The full preflight and behavior matrix are in the [Frozen lockfile specification](/specification/commit#frozen-lockfile).

  Frozen mode **never prompts**, even in a fully interactive terminal. It reproduces recorded intent, so it must not collect a new decision. A name collision under `--frozen-lockfile` is reported and fails, and MCP configuration needing approval fails unless [`--accept-mcp`](#param-accept-mcp) was supplied.

  A `0.2` lockfile has no field in which to record an **asset** materialization disposition. If `facets.json` declares any asset override against one, the frozen install fails rather than silently ignoring it — run one non-frozen `facet install` to migrate the lockfile. A `materialization.servers` override can never cause this: no lockfile version records server intent, by design.

  Frozen mode reads `manifestVersion` `0.2`, `0.1`, and unversioned documents, and migrates none of them. A stale `servers` override — one naming a server the locked facet no longer declares — is reported as blocking drift and is **not** removed.

  <Tip>
  Use this in CI to guarantee `facets.json` and `facets.lock` are in agreement. Mirrors `--frozen-lockfile` from `npm` and `bun`.
  </Tip>
</ResponseField>

## Exit codes

| Code | Meaning                                                              |
| ---- | -------------------------------------------------------------------- |
| `0`  | Install succeeded (including no-op when nothing has changed).        |
| `1`  | Install failed. The view renders the structured failure inline; stderr carries a three-line block — `error:`, `code=...` for log-grepping, and a `fix:` action. A [name collision](#name-collisions), an [MCP approval requirement](#in-ci-and-other-non-interactive-runs), and an [unsupported adapter](#adapters-that-cannot-configure-mcp-servers) each print a full report above that block, so `fix:` stays the last line. |

## What it does

<Steps>
  <Step title="Validate the project">
    `facets.json` must exist, and at least one **install-capable** adapter must be installed. If none are, the picker launches when the terminal can prompt; otherwise the command exits pointing at [`facet adapter add`](/cli/adapters/add). Installed-but-incompatible adapters fail here rather than falling through to the picker.
  </Step>
  <Step title="Run the install pipeline">
    Runs the [install pipeline](/specification/install) with an empty delta: acquire the install lock, resolve and [verify](/specification/commit#verify) *every* declared facet ([honoring satisfying lockfile pins](/specification/commit#resolve)), [compose one global plan](/specification/commit#compose) checking for name collisions, check that every selected adapter can configure any active MCP servers, ask each adapter to [prepare](/specification/commit#reconciliation) its native MCP change read-only, obtain [MCP approval](#mcp-servers), then [remove drift](/specification/commit#drift-removal) and materialize assets into every adapter, apply the prepared MCP changes, and finally [write manifest + lockfile + receipt atomically](/specification/commit#transactional-tri-write).

    Deletion runs before any write, which is what lets an asset name move from one facet to another in a single install. MCP configuration is applied **last**, immediately before the tri-write.
  </Step>
</Steps>

<Note>
Every facet is verified, the whole plan composed, every adapter's MCP change prepared, and every approval collected before any asset is written. An integrity mismatch, a name collision, a cancelled resolution, a declined MCP approval, an unsupported adapter, and an unparseable tool config all abort with the project **byte-identical** — not rolled back, but never touched.

Cancelling an [asset takeover](#taking-over-an-existing-file) is the exception: it happens mid-write, so it is a genuine rollback rather than an untouched abort. The full semantics live in the [Commit specification](/specification/commit) and the [Integrity Model](/specification/integrity).
</Note>

## Outcomes

The summary line classifies each facet by what happened on disk:

<ResponseField name="installed" type="new">
  Facet was not in the previous lockfile.
</ResponseField>

<ResponseField name="updated" type="state change">
  Facet was in the lockfile at a different version  -- including when a stale entry was re-resolved to match the manifest. The summary shows `(was X → Y)`.

  Also reported when the version is unchanged but its [materialization](/specification/materialization) is not: aliasing or omitting an asset **or an MCP server**, or a changed server declaration, changes what the project materializes, so it is an update rather than a no-op. It is not a *repair* either — nothing drifted, the project changed its mind.
</ResponseField>

<ResponseField name="repaired" type="self-heal">
  Same version and same materialization intent, but at least one adapter file was missing or had drifted from the lockfile content. Restored. A skill is repaired by replacing its whole bundle atomically, so a single drifted companion pulls the primary with it.

  MCP configuration is repaired the same way: an already-approved declaration whose native entry had drifted is rewritten, as is a divergent untracked entry you chose to take over.
</ResponseField>

<ResponseField name="unchanged" type="no-op">
  Same version, same materialization intent, every asset already in its desired state. Nothing was written — the on-disk bytes were compared and matched, which is enough to record the assets as tracked without rewriting them.

  A native MCP entry that already matches semantically is likewise left untouched, including one you took over: adopting an equivalent entry records ownership without rewriting the document.
</ResponseField>

<ResponseField name="removed" type="cleanup">
  Facet is no longer declared in `facets.json`, and this machine's [install receipt](/specification/commit#machine-local-install-receipt) tracked it. Its ownership was reconciled: obsolete identities deleted, and any identity another declared facet now claims kept. That includes MCP server entries the receipt owned — the complete entry is removed from every selected adapter, while an entry the receipt never claimed is left alone.
</ResponseField>

<ResponseField name="removed-untracked" type="records only">
  Facet is no longer declared, and only the lockfile ever recorded it — you pulled a teammate's `facets.lock` and never installed. The declaration is dropped from `facets.json` and `facets.lock`, but **nothing on disk is deleted**, because no receipt claim proves this machine wrote it. The summary names the facet and says the files were left in place.
</ResponseField>

<Note>
The `N removed` count covers both: it counts declarations that went away. How many *assets* left disk is the separate asset count — zero, for an untracked removal.
</Note>

If you delete a materialized asset by hand and re-run `facet install`, the affected facet shows up as `repaired`.

MCP servers are counted **separately** from text assets, so a facet that contributes only servers reports real work rather than looking like a no-op:

```
  1 installed · 0 assets written · 1 server config added
  mcp-tools MCP server filesystem added in claude-code, opencode
```

Server configuration is reported as `added`, `updated`, `repaired`, `unchanged`, or `removed`, with `aliased` and `omitted` counted alongside their asset equivalents. A line gains ` (took over an existing entry)` when the entry was [taken over](#taking-over-an-existing-entry) rather than created.

Below the counts, the summary names every contribution whose materialized name differs from its authored one — the one thing you cannot infer from the file tree:

```
  1 updated · 1 asset written · 1 server config updated
  + 1 skill
  viper-plans skill planning → team-planning
  cowsay command scratch — omitted
  mcp-tools server filesystem → team-filesystem
  mcp-tools server docs — omitted
```

Omitted assets and omitted servers are not counted as written.

## Name collisions

Two facets cannot materialize a contribution under the same name. Skills and commands share one namespace; agents have their own; MCP servers are a third, separate space — see [Namespaces](/specification/materialization#namespaces). A server never collides with a skill, command, or agent.

Two facets declaring the **same** server, spelled the same way, is not a collision: identical declarations compose into one configuration and both facets are recorded as claimants. Only differing declarations at one effective name contest it.

Collisions are detected **globally, before anything is written**, so the install stops with the project untouched.

**In an interactive terminal**, the install pauses and opens a resolver. Each contested asset gets one of three outcomes:

| Key | Choice | Result |
| --- | --- | --- |
| `Keep` | keep the authored name | records nothing |
| `Alias` | materialize under a name you type | `{ "kind": "aliased", "as": "..." }` |
| `Omit` | do not materialize it at all | `{ "kind": "omitted" }` |

Move with `↑↓`, pick with `←→`, apply with `Enter`, and `Esc` to go back. Arrow keys only move the cursor — nothing is applied until you press `Enter`. Each claimant shows a status that pairs an icon with a word, so it stays readable without color: `✕ unresolved`, `⚠ conflict` (your own edit created this one), `✓ resolved`. Confirmation unlocks only when every group is resolved.

A contested server claimant additionally shows its declaration summary and a short fingerprint (`stdio, command "npx" · 1a2b3c4d`) so you can tell two same-named servers apart without leaving the screen.

Your choices are written into `facets.json` as durable intent, so the next install runs without prompting:

```json facets.json
"viper-plans": {
  "source": "1.*",
  "materialization": {
    "skills": { "planning": { "kind": "aliased", "as": "team-planning" } },
    "servers": { "filesystem": { "kind": "aliased", "as": "team-filesystem" } }
  }
}
```

The `servers` group requires `"manifestVersion": 0.2`. A successful non-frozen install writes that version for you; a `servers` group inside a document that declares `0.1` is rejected rather than tolerated.

`Esc` or `Ctrl-C` cancels the whole install. Nothing was written, and re-running lets you make the choices again.

**Without a terminal** — CI, piped output, or `--frozen-lockfile` — nothing is prompted. Every group and every claimant is printed to stderr with the exact `facets.json` location to edit and copy-pasteable alias and omit snippets. No winner is chosen and no alias is invented for you: the placeholder is literally `choose-a-name`. The report ends by stating that `facets.json`, `facets.lock`, the receipt, your materialized assets, and every tool's MCP configuration were **not** changed.

## Cache

Resolved facet content is stored at `$FACET_DIR/cache/<name>@<version>/` (default `~/.facet/cache/`) so subsequent installs of the same identity don't hit the network. Cache hits are re-verified on every use — see [cache self-audit](/specification/integrity). The cache root is part of the facet directory tree; set `FACET_DIR` to change it. See the [environment variables reference](/cli/env).

## MCP servers

A facet that declares [`servers`](/specification/manifest#mcp-server-declarations) contributes MCP server configuration to every selected adapter, written into each tool's own project file — `.mcp.json` for Claude Code, `opencode.jsonc` and `opencode.json` for OpenCode, `.codex/config.toml` for Codex. Only project-scoped files are ever touched; no user- or system-wide tool configuration is created or modified.

OpenCode merges its two configuration files, so both are read and both count as one configuration. A new entry goes to `opencode.jsonc` when that file exists, otherwise to an existing `opencode.json`, and otherwise into a newly created `opencode.jsonc`. An existing entry is updated in whichever file it currently wins in — and when your project owns an entry defined in both, the `opencode.jsonc` copy is updated and the shadowed `opencode.json` copy is removed in the same change. An entry your project owns is removed from every file that defines it. Entries you added yourself are never touched in either file.

Installing a server **configures** it. Facets never downloads it, launches it, connects to it, checks its health, or authenticates to it. Whatever sign-in the server needs happens inside your coding tool afterwards.

### Approving a declaration

Approving MCP configuration means letting your coding tools run a command or open a connection, so a new or changed declaration is never written without your say-so.

In an interactive terminal the install pauses on one MCP-only screen listing every declaration awaiting approval, each with its claimant facets and its **exact** command, arguments, and environment assignments — or its exact URL. `Decline` is selected by default; `←/→` chooses, `Enter` confirms, and `Esc` or `Ctrl-C` declines. Approval is all-or-nothing over the displayed set.

Approval is remembered **per machine**, keyed by the effective server name and the declaration's content:

- Reproducing an already-approved declaration does not ask again — including when a second facet declares the same server identically.
- Changing the command, argument order, an environment value, the transport, the URL, or the effective name asks again.
- A run that fails or is rolled back banks nothing; the next attempt asks again.

<Note>
Approval never travels with your project. It lives in the machine-local [install receipt](/specification/commit#machine-local-install-receipt), not in `facets.json` or `facets.lock`, so a teammate who clones your fully-approved project approves it on their own machine. That is deliberate: committed files must not be able to claim you consented to running something.
</Note>

### In CI and other non-interactive runs

Without a terminal, an unapproved declaration fails the install **before anything is written** and prints the complete list to stderr: every effective server name, its claimant facets, its full declaration, and — per claimant — the exact `facets.json` location and a copy-pasteable omission snippet.

You then have two ways forward: re-run with [`--accept-mcp`](#param-accept-mcp) to approve everything shown, or record an omission for the servers you do not want.

```json facets.json
"mcp-tools": {
  "source": "1.*",
  "materialization": {
    "servers": { "filesystem": { "kind": "omitted" } }
  }
}
```

### Taking over an existing entry

If a desired server name already has an entry that this project's receipt does not own — you configured it by hand, or a teammate did — it is disclosed in a distinct section of the same approval screen, before anything is written. Each line names the adapter and says whether the existing entry `already matches and would be adopted` or `differs and would be replaced`.

An equivalent entry is adopted **without rewriting the document**; a divergent one is replaced transactionally. An entry the receipt already owns reconciles with no disclosure, and an entry outside your desired set is never touched at all. Because this happens before the first write, declining has nothing to undo.

### Taking over an existing file

Assets have their own, separate takeover prompt, and it behaves differently on purpose. It appears **mid-write**, at the moment materialization reaches an occupied destination this machine does not own, naming the adapter, scope, type, and effective name.

`Continue` is the default here — the opposite of MCP consent — because continuing is what a non-interactive run already does, and because taking over a file is far less consequential than authorizing a command to run. Cancelling **rolls back everything the command has done so far** and exits non-zero. Non-interactive runs continue automatically with no prompt.

`--accept-mcp` never answers this screen.

### Adapters that cannot configure MCP servers

Configuring servers needs an adapter that declares MCP support. When active declarations exist and a selected adapter cannot serve them, the install fails before approval and before any mutation, naming **every** such adapter.

The adapter declares no MCP support, and a newer release will not change that: omit the declarations in `facets.json`, or deselect the adapter.

Omitting every declared server also resolves this: with no active declarations, an adapter without MCP support is perfectly usable.

### Where declarations appear

A declaration's command, arguments, environment values, and URL are shown on exactly two surfaces: the interactive approval screen, and the non-interactive report that asks you to approve. They never appear in `--verbose` output, in success summaries, or in other diagnostics, which name servers by identity only. That keeps the contents of a declaration out of scrollback and CI logs.

On both surfaces every value is shown quoted and escaped — `"srv" "--root" "/w"`, `"TOKEN"="a b"`. Nothing is hidden or shortened; the quoting is what keeps one argument containing a space distinguishable from two arguments, and what stops a value from adding a line or issuing a terminal escape of its own.

The non-interactive report also lists every existing entry the run would take over: the adapter, the effective name, whether the entry already matches or differs, and the full declaration that would be adopted or written. It ends by stating that nothing was changed.

<Warning>
`env` values are literal strings that ship inside the published facet. Never put a token, key, or other secret in one. Authenticate inside your coding tool instead.
</Warning>
