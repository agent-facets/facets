---
title: facet update
description: Move declared facets to newer releases
---

## Usage

```sh
facet update
```

Checks every registry-backed facet in `facets.json` for a newer release, then installs the ones that move. Applying an update is an ordinary [install](/cli/install), so it reports the same outcomes and honors the same approvals.

`facet upgrade` is an alias of this command, with the same flags, output, and exit codes. Both act on the facets your project declares. To update the `facet` binary, use [`facet self-update`](/cli/self-update).

`facet update` takes no positional arguments. To update some facets but not others, use `--interactive`.

## Examples

```sh
facet update                    # newest release each declared range allows
facet update --latest           # newest release, ignoring ranges
facet update --dry-run          # print the plan, change nothing
facet update --interactive      # choose per facet, and which version each takes
```

## Flags

<ResponseField name="--latest" type="boolean">
  Take each facet's latest release, ignoring the range in `facets.json`. Short form `-L`.

  This is the only mode that rewrites a specifier. See [Crossing the declared range](#crossing-the-declared-range).

  It has no effect alongside `--interactive`, which already opens every row on its latest release.
</ResponseField>

<ResponseField name="--interactive" type="boolean">
  Choose which facets move and which version each takes. Short form `-i`.

  Requires a terminal. Without one the command fails before contacting the registry.
</ResponseField>

<ResponseField name="--dry-run" type="boolean">
  Print the plan and modify nothing. Exits `0` whether or not updates are available.
</ResponseField>

<ResponseField name="--verbose" type="boolean">
  Show detailed step output on stderr. Declaration contents never appear here. See [where declarations appear](/cli/install#where-declarations-appear).
</ResponseField>

<ResponseField name="--accept-mcp" type="boolean">
  Approve the [MCP configuration](/cli/install#accept-mcp) this update would write, without prompting.
</ResponseField>

<ResponseField name="--json" type="boolean">
  Print one JSON document to stdout instead of the plan view, and turn off the live progress indicator so its frames can't land in front of the document. Cannot be combined with `--interactive`: the picker writes to the same stream the document would. See [JSON output](#json-output).
</ResponseField>

There is no `--frozen-lockfile` here. Frozen mode reproduces what the lockfile records, which is the opposite of what this command does, and it belongs to [`facet install`](/cli/install#frozen-lockfile).

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Updates applied, a successful [no-op](#when-nothing-moves), or a completed `--dry-run`. |
| `1` | The command refused to run, the picker was cancelled or unavailable, or the install failed. See [Troubleshooting](#troubleshooting). |
| `2` | An unexpected error escaped command handling. |

## Output

```
  1 updated · 2 assets written
  viper-plans 1.2.0 → 1.4.0
```

Each moving facet is named with the version it left and the version it took. Recorded aliases and omissions survive a version change, and outcomes match [`facet install`](/cli/install#outcomes).

## JSON output

`--json` prints one document to stdout and nothing else — no plan view, no progress indicator. The exit code and the document answer two different questions: the exit code says whether the command *worked* (`0` for every successful run, whether or not anything moved, including a no-op or a completed `--dry-run`; `1` when preparation, selection, or the install itself failed — see [Exit codes](#exit-codes)), and the document's `applied` field and each facet's `outcome` say whether anything *moved*. Check the exit code first; read the document for what happened.

A project that pins `cowsay` at `1.0.0`, with `1.0.1` published to the registry, run through `facet update --latest --json`:

```json
{
  "schemaVersion": "1",
  "ok": true,
  "applied": true,
  "facets": [
    {
      "name": "cowsay",
      "declared": "1.0.0",
      "current": "1.0.0",
      "target": "1.0.0",
      "latest": "1.0.1",
      "outcome": "updated"
    }
  ],
  "counts": { "updated": 1, "current": 0, "held": 0, "unsupported": 0 }
}
```

<ResponseField name="applied" type="boolean">
  Whether this run actually wrote. `false` for a dry run; `true` once `facets.json`, `facets.lock`, and any assets have been written.
</ResponseField>

<ResponseField name="facets" type="array">
  One entry per declared facet, each with `declared` (the specifier exactly as written in `facets.json`), `current` (the installed version), `target` (the newest release the declared range permits), `latest` (the registry's newest release), and `outcome`.
</ResponseField>

Each facet's `outcome` is one of four values:

<ResponseField name="updated" type="outcome">
  This run's flags take a newer release for it — `target` under a plain update, `latest` under `--latest`.

  `outcome` says what the flags resolve to, not whether anything was written. Read `applied` for that: a preview (`--dry-run`, or [`facet outdated`](/cli/outdated)) reports `applied: false` while still marking movable facets `updated`, because that is what the same flags would do for real.
</ResponseField>

<ResponseField name="current" type="outcome">
  Already at the newest release that exists. Nothing to take.
</ResponseField>

<ResponseField name="held" type="outcome">
  A newer release exists, but this run doesn't take it. A facet pinned to an exact version, or floating within a range that doesn't reach the newest release, shows `held` — plain words for "the ranges in `facets.json` permit none of them" — until it runs with `--latest`. A fully pinned project sees `held` rather than `updated` until then.
</ResponseField>

<ResponseField name="unsupported" type="outcome">
  A git or local source. Not checked for updates; `current`, `target`, and `latest` are all `null`.
</ResponseField>

`counts` tallies how many facets landed in each outcome, always summing to `facets.length`.

On failure the document takes a different shape and the exit code is `1`:

```json
{
  "schemaVersion": "1",
  "ok": false,
  "error": {
    "what": "facets.json declares a source that cannot be parsed",
    "detail": "cowsay: \"not-a-version\" is not a valid specifier",
    "fix": "correct that entry in facets.json by hand"
  }
}
```

## Details

### Current, Target, and Latest

Every checkable facet has three versions, and the plan shows all three:

<ResponseField name="current" type="installed">
  The exact version `facets.lock` records.
</ResponseField>

<ResponseField name="target" type="range-respecting">
  The newest release the specifier in `facets.json` already permits. Taking it never changes what the project declares.
</ResponseField>

<ResponseField name="latest" type="newest published">
  The registry's newest release, whatever the specifier says.
</ResponseField>

All three appear even for a facet that is not moving, because that is what answers why it stayed put:

```
  facet        declared  current  target  latest
▸ viper-plans  1.*       1.2.0    1.4.0   2.0.0
  cowsay       2.1.*     2.1.3    2.1.3   3.0.0
```

`viper-plans` moves to `1.4.0` under a plain update. `cowsay` does not move, and reaching `3.0.0` needs `--latest`.

Plain `facet update` takes every Target that advances. `--latest` takes every Latest that advances.

### Crossing the declared range

`--latest` can select a version the declared specifier forbids, so it rewrites that specifier with the smallest edit that admits the new version:

```
    facets.json 1.* → 2.*
```

A pin stays a pin, a wildcard keeps its shape, and a specifier that already floats is left as written. The full table is in the [manifest write policy](/specification/install#manifest-write-policy).

Taking a Target never rewrites anything.

### Choosing interactively

```
    facet        current  target  latest
▸ ○ viper-plans  1.2.0    1.4.0   2.0.0  (latest)
  ○ cowsay       2.1.3    2.1.3   3.0.0  (latest)
```

```
↑↓ move · ◀ ▶ target/latest · Space select · Enter confirm · Esc cancel
```

Every row opens on its Latest with nothing selected, so `Space` takes the newest release of that facet and a facet you never touch is left alone. Move a row to `target` first to take the version your declared range already permits.

Only the digit that moves is coloured, and the column a row would install is also named in words, so the screen works without colour. A row already at the installed version cannot be selected, and confirming needs at least one selection.

Selection happens before adapter discovery and before anything is written, so cancelling costs nothing.

### Previewing

`--dry-run` prints the plan and writes nothing: no manifest, no lockfile, no assets, no cache, and no adapter installation. That also means a preview works on a machine with no adapter connected.

A preview always prints the plan, including when nothing would move, followed by the reason. A real run prints the reason alone. Combined with `--interactive` it previews the selection you confirmed.

<Note>
  A preview shows versions, not their effects. Which assets a release materializes, whether it collides, and what it declares are determined during the install a real run performs.
</Note>

### When nothing moves

A run that applies nothing still succeeded and exits `0`.

| Output | What it means |
| --- | --- |
| `No registry facets to update.` | Nothing in the project is registry-backed. |
| `All registry facets are current.` | Every facet is at the newest release that exists. |
| `Newer releases exist, but the ranges in facets.json permit none of them.` | Your specifiers forbid what was published. Take them with `--latest`. |
| `No registry facet has a newer release than the one installed.` | Under `--latest`, with nothing left to suggest. |

### Sources that cannot be checked

Only registry facets have releases to compare. Git and local facets are named in the printed plan rather than counted as current:

```
  scratch — local source (./packages/scratch); not checked for updates
```

Because a plain run prints only the reason, use `--dry-run` to see these rows. Move one by editing its source in `facets.json` and running [`facet install`](/cli/install).

## Troubleshooting

<AccordionGroup>
  <Accordion title="this project cannot be checked for updates yet">
    **Cause:** `facets.json` and `facets.lock` disagree. A declared registry facet is missing from the lockfile, locked to a different source kind, locked at something that is not an exact release, or locked at a version its specifier no longer permits. The message names every affected facet.

    **Fix:** repair the drift first, then update:

    ```sh
    facet install
    facet update
    ```
  </Accordion>

  <Accordion title="facets.json declares a source that cannot be parsed">
    **Cause:** an entry's specifier is malformed, so update cannot tell what it is meant to resolve to.

    **Fix:** correct that entry in `facets.json` by hand. `facet install` cannot repair a malformed specifier.
  </Accordion>

  <Accordion title="the project changed while the update ran">
    **Cause:** `facets.json` or `facets.lock` changed while the plan was being built, or between reading the plan and applying it. A concurrent command, a pull, or an editor save will do it.

    **Fix:** re-run `facet update`. Nothing was written in either case, so nothing needs repairing.
  </Accordion>

  <Accordion title="facet update --interactive needs an interactive terminal">
    **Cause:** the picker needs a TTY. The check runs before any registry lookup.

    **Fix:** use a non-interactive mode instead:

    ```sh
    facet update            # every range-respecting target
    facet update --latest   # every latest release
    facet update --dry-run  # print the plan, change nothing
    ```
  </Accordion>

  <Accordion title="the update selection screen could not be shown">
    **Cause:** the terminal check passed, but the picker could not render, for example because stdin was taken away mid-run.

    **Fix:** re-run in a normal terminal, or pick a non-interactive mode. Nothing was applied.
  </Accordion>

  <Accordion title="facet update does not accept positional arguments">
    **Cause:** update considers everything declared in `facets.json`.

    **Fix:** choose per facet with `facet update --interactive`.
  </Accordion>

  <Accordion title="the registry returned an unusable version">
    **Cause:** the registry answered with something that is not an exact release, or resolved a facet outside its declared range. Your project cannot cause this.

    **Fix:** retry shortly. If it persists, report it with the facet name from the message.
  </Accordion>
</AccordionGroup>
