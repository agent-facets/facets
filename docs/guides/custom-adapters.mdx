An <Tooltip headline="Adapter" tip={<span>The bridge between facets and an AI coding tool. It tells <code>facet</code> where and how to write a facet's assets on disk so the tool can find them.</span>} cta="Adapter reference" href="/cli/adapters/install">adapter</Tooltip> teaches the `facet` CLI how to install assets into a specific AI coding tool. The first-party adapters cover Claude Code, OpenCode, and Codex; this guide shows how to build your own using the [`@agent-facets/adapter`](https://github.com/agent-facets/facets/tree/main/packages/adapter) SDK.

An adapter is a small TypeScript library. You write one file, build it, and install it locally  -- from a directory, from GitHub, or (once published) by name.

<Visibility for="agents">

> **Building an adapter?** It's a TypeScript package that default-exports a
> `defineAdapter({...})` call. The contract lives in `@agent-facets/adapter`:
>
> - `name` (required) — unique adapter id.
> - `buildAssetMetadata(data)` (required) — validate/enrich per-asset
>   manifest metadata; return `Validated<AdapterMetadata>`.
> - `supportsInstall: true` + `installAsset` / `readAsset` / `deleteAsset` —
>   the filesystem I/O that materializes assets. Each takes a single request
>   object **tagged by `assetType`** and returns a discriminated result
>   (`{ ok: true, … }` or `{ ok: false, failure }`) — expected failures are
>   values, never thrown. Without these the adapter is metadata-only and
>   hidden from the install picker.
> - `mcpServers` (**required**) — `false`, or a complete MCP server capability
>   `{ prepare, apply }`. It is a union, not a boolean plus optional methods,
>   so a partial capability cannot be expressed. `false` is a legitimate
>   permanent answer; the adapter then blocks any project with active MCP
>   declarations rather than silently skipping them.
>   - `prepare(request)` is **read-only**: parse your tool's project config,
>     classify every desired server (`absent` / `equivalent` / `divergent`,
>     each with `ownership`, plus `obsolete-owned`), disclose every document
>     the change could touch in `documentPaths`, and return an opaque `plan`.
>     Write nothing — not even when the document does not exist yet.
>   - `apply({ plan })` performs one atomic update per document and returns
>     `unchanged` or `changed` + `changedPaths` (a subset of what you
>     disclosed). There is **no** inverse method: the engine journals byte
>     preimages and restores them itself.
>   - Ownership comes from `previouslyOwnedNames` in the request. Never infer
>     it from the document. `name` is already the effective name.
>   - Classify as `divergent` whenever you cannot *prove* semantic equality.
>   - Preserve unrelated settings and any server entry that is neither desired
>     nor owned.
>
> Use the SDK's skill-bundle helpers (`installSkillBundle` /
> `readSkillBundle` / `deleteSkillBundle`) for the multi-file skill variant,
> and the single-file helpers (`installSingleFileAsset` /
> `readSingleFileAsset` / `deleteSingleFileAsset`) for agents and commands.
> `Scope` is `'system' | 'user' | 'project'`; `AssetType` is
> `'skill' | 'agent' | 'command'`.
>
> `defineAdapter()` stamps the adapter API version (`apiVersion`, currently
> `0.2`) onto the returned adapter — do NOT set it yourself; the input type
> excludes it, and a value supplied through untyped input is ignored. `0.2`
> identifies the tagged request/result asset contract plus the `mcpServers`
> capability; `0.1` is the asset-only contract; the earlier positional
> contract (`0.0`) is unsupported. The current CLI supports exactly
> `{0.1, 0.2}` — membership is exact, never ordering or proximity. When
> publishing to npm, the published `package.json` MUST declare
> `"facetAdapterApiVersion": "0.2"` (the canonical constants live at
> `@agent-facets/adapter/api-version`) and it MUST match what your bundle
> stamps at runtime, or verification fails.
>
> Build with `tsdown`/`tsc`, then install:
>
> ```sh
> facet adapter install ./my-adapter                        # local directory
> facet adapter install git+https://github.com/you/repo.git # from GitHub
> facet adapter install my-adapter                           # by npm name, once published
> ```

## How an adapter fits in

When you run `facet install`, the CLI resolves each facet's contributions and hands the ones the project wants materialized to every installed adapter. The adapter decides **where** on disk each asset goes and **how** it's formatted, so the target tool picks it up.

There are two halves to the job:

- **Assets** — translate a facet's skills, agents, and commands into files your tool reads. You own the layout.
- **MCP servers** — translate portable server declarations into your tool's own project configuration. You own the format, and you edit a file the user may already be using.

An adapter implements a small contract from the SDK:

- `buildAssetMetadata` validates the per-asset metadata an author put in `facet.json` (the `adapters.<name>` block) and enriches it with your defaults.
- `installAsset` writes the asset to disk. Its siblings `readAsset` and `deleteAsset` complete the lifecycle.
- `mcpServers` declares whether you configure MCP servers, and if so, how. It is **required** — see [MCP server configuration](#mcp-server-configuration).

## Scaffold the package

<Steps>

<Step title="Create a package and add the SDK">

```sh
mkdir my-adapter && cd my-adapter
bun init -y
bun add @agent-facets/adapter
```

The SDK is a leaf library with no heavy dependencies  -- `@agent-facets/common` (the shared types) is bundled into it, so you don't install anything else.

</Step>

<Step title="Write the adapter">

Create `src/index.ts` and default-export a [`defineAdapter`](https://github.com/agent-facets/facets/tree/main/packages/adapter) call. Each I/O method takes a single request **tagged by `assetType`** and returns a discriminated result. Skills are multi-file bundles (a primary `SKILL.md` plus companion files); agents and commands are single files. The SDK's bundle and single-file helpers do the heavy lifting:

```ts expandable src/index.ts
import {
  defineAdapter,
  installSkillBundle,
  readSkillBundle,
  deleteSkillBundle,
  installSingleFileAsset,
  readSingleFileAsset,
  deleteSingleFileAsset,
  type InstallAssetRequest,
  type ReadAssetRequest,
  type DeleteAssetRequest,
  type SkillBundlePaths,
  type Validated,
  type AdapterMetadata,
} from '@agent-facets/adapter'
import { homedir } from 'node:os'
import { join } from 'node:path'

const baseDir = join(homedir(), '.my-tool')

// A skill lives in its own directory: skills/<effective name>/SKILL.md (+ companions).
function skillPaths(name: string): SkillBundlePaths {
  const root = join(baseDir, 'skills', name)
  return { root, primaryFile: join(root, 'SKILL.md'), pruneBoundary: baseDir }
}

export default defineAdapter({
  name: 'my-tool',
  supportsInstall: true,

  // Required. `false` is a complete, permanent answer: this adapter does not
  // configure MCP servers. See "MCP server configuration" below to implement it.
  mcpServers: false,

  // Validate the author's `adapters.my-tool` block at build time.
  // Returns errors if it's invalid; the CLI writes front matter itself.
  buildAssetMetadata(data: unknown): Validated<AdapterMetadata> {
    // Trivial pass-through; use arktype/zod here for a real schema.
    const meta = (data ?? {}) as AdapterMetadata
    return { ok: true, data: meta }
  },

  // Branch on request.assetType. Skills carry a companion byte map plus the
  // engine-verified owned-companion path set; the bundle helper stages,
  // rolls back, and prunes atomically. Agents and commands are single files.
  async installAsset(request: InstallAssetRequest) {
    switch (request.assetType) {
      case 'skill':
        return installSkillBundle(skillPaths(request.name), {
          content: request.content,
          metadata: request.metadata as Record<string, unknown>,
          companions: request.companions,
          ownedCompanionPaths: request.ownedCompanionPaths,
        })
      case 'agent':
        return installSingleFileAsset(
          { file: join(baseDir, 'agents', `${request.name}.md`) },
          request.content,
          request.metadata as Record<string, unknown>,
        )
      case 'command':
        return installSingleFileAsset(
          { file: join(baseDir, 'commands', `${request.name}.md`) },
          request.content,
          request.metadata as Record<string, unknown>,
        )
    }
  },

  async readAsset(request: ReadAssetRequest) {
    switch (request.assetType) {
      case 'skill':
        return readSkillBundle(skillPaths(request.name), request.ownedCompanionPaths)
      case 'agent':
        return readSingleFileAsset({ file: join(baseDir, 'agents', `${request.name}.md`) }, 'agent')
      case 'command':
        return readSingleFileAsset({ file: join(baseDir, 'commands', `${request.name}.md`) }, 'command')
    }
  },

  async deleteAsset(request: DeleteAssetRequest) {
    switch (request.assetType) {
      case 'skill':
        return deleteSkillBundle(skillPaths(request.name), request.ownedCompanionPaths)
      case 'agent':
        return deleteSingleFileAsset({ file: join(baseDir, 'agents', `${request.name}.md`), pruneBoundary: baseDir })
      case 'command':
        return deleteSingleFileAsset({ file: join(baseDir, 'commands', `${request.name}.md`), pruneBoundary: baseDir })
    }
  },
})
```

<Note>
  The bundle helpers (`installSkillBundle` / `readSkillBundle` / `deleteSkillBundle`) and single-file helpers (`installSingleFileAsset` / …) manage YAML front-matter, directory creation, atomic staging with rollback, and byte-stable round-trips. Skill helpers only ever touch the primary file plus the caller-supplied owned companion paths, so unowned user files are never read, deleted, or swept into a result. Use them instead of hand-rolling file I/O so re-installs don't report phantom drift.
</Note>

</Step>

</Steps>

## The adapter contract

Everything an adapter can implement, from [`@agent-facets/adapter`](https://github.com/agent-facets/facets/tree/main/packages/adapter):

<ResponseField name="name" type="string" required>
  A unique id (e.g. `my-tool`). Users install and reference the adapter by this name.
</ResponseField>

<ResponseField name="apiVersion" type="string">
  The adapter API contract the adapter was built against — **stamped automatically by `defineAdapter()`** (currently `0.2`: the tagged request/result asset contract plus the MCP server capability). You cannot set it in your definition; the input type excludes it, and a value forced through untyped input is ignored rather than honored.

  The CLI classifies a declared API as missing, malformed, unsupported, or supported, and supported means **membership in an explicit set** — currently `{0.1, 0.2}`. Compatibility is never inferred from the CLI version, the SDK package version, your package version, or semver ordering, and numeric proximity confers nothing: `0.0` is not "nearly `0.1`". An adapter built against the positional `0.0` contract must be rebuilt and reinstalled.
</ResponseField>

<ResponseField name="buildAssetMetadata(data)" type="Validated<AdapterMetadata>" required>
  Validate and enrich the per-asset metadata from a facet's `adapters.<name>` block. Return `{ ok: true, data }` or `{ ok: false, errors }`. Runs during `facet build`, so bad config is caught early.
</ResponseField>

<ResponseField name="supportsInstall" type="boolean">
  Set to `true` only when all three I/O methods below are implemented. It makes the adapter selectable in the install picker; a metadata-only adapter omits it and stays hidden.
</ResponseField>

<ResponseField name="mcpServers" type="false | McpServerCapability" required>
  Whether this adapter configures MCP servers, and how. See [MCP server configuration](#mcp-server-configuration) for the full capability. It is a **union**, deliberately: a boolean plus optional methods could disagree with itself, so a partially implemented capability is unrepresentable rather than merely discouraged.

  The field is MCP-specific. A future project-configuration feature gets its own capability rather than widening this one.
</ResponseField>

<ResponseField name="installAsset(request: InstallAssetRequest)" type="Promise<InstallAssetResult>">
  Install (or replace) an asset. `request` is tagged by `assetType`: the `skill` variant carries `content`, `metadata`, a `companions` byte map, and the engine-verified `ownedCompanionPaths`; `agent`/`command` variants carry `content` and `metadata` only. Return `{ ok: true, primaryPath }` or `{ ok: false, failure }`.
</ResponseField>

<ResponseField name="readAsset(request: ReadAssetRequest)" type="Promise<ReadAssetResult>">
  Read an asset back. The `skill` variant carries `ownedCompanionPaths` (read exactly those, never enumerate the directory). Your `readAsset` must be a byte-stable inverse of `installAsset` — the engine compares what it reads back against what it would write to decide whether a facet is unchanged, so any asymmetry reports phantom drift on every install. Return `{ ok: true, asset }` or `{ ok: false, failure }` (`failure.code === 'not-found'` when absent).
</ResponseField>

<ResponseField name="deleteAsset(request: DeleteAssetRequest)" type="Promise<DeleteAssetResult>">
  Remove an asset. The `skill` variant carries `ownedCompanionPaths`; deletion removes the primary plus exactly those, preserving unowned files. That set is the union of every past claim on this name, so it may include files a *different* facet left behind when the name changed hands. Deletes run before writes in a single install, so expect to be asked to delete and then re-create the same name. Return `{ ok: true, existed, deletedPaths }` or `{ ok: false, failure }`.
</ResponseField>

Every request carries `scope` (`'system'`, `'user'`, or `'project'` — decide your on-disk layout per scope) and `name`, tagged by `assetType` (`'skill'`, `'agent'`, or `'command'`). `name` is always the effective name (see above); by the time a request reaches you the effective set is guaranteed collision-free, so you never have to arbitrate between two assets wanting one path. Expected failures are structured values (`not-found`, `invalid-companion-path`, `unsupported-scope`, `not-implemented`, `io-failed`), never thrown errors.

<Tip>
  You can ship a **metadata-only** adapter: implement just `name`, `buildAssetMetadata`, and `mcpServers: false`, and omit `supportsInstall`. It validates manifest config during builds without materializing anything  -- useful while you're still figuring out a tool's on-disk layout.
</Tip>

## MCP server configuration

A facet can declare [MCP servers](/specification/manifest#mcp-server-declarations). Adapter API `0.2` adds one capability for turning those portable declarations into your tool's own project configuration.

```ts
mcpServers: false | { prepare, apply }
```

`false` says your tool has no MCP configuration to write. That is a complete answer, not a stub: a project with no active declarations installs normally, and a project with them fails with a clear message naming your adapter.

<Note>
Declarations come from `@agent-facets/protocol` — import the type, never restate its shape. One portable declaration reaches every adapter; you translate it, rather than copying another tool's file format.
</Note>

### Prepare, then apply

The capability is deliberately split, and both halves operate on the **complete** desired set rather than one server at a time.

<ResponseField name="prepare(request)" type="Promise<PrepareResult>" required>
  Strictly read-only. Parse your tool's project document **once**, work out the whole change, and write nothing — including when the document does not exist yet. Describe the prospective file instead of creating it.

  The request carries `projectRoot`, the complete `desired` contribution set, and `previouslyOwnedNames`: the effective names the engine has verified this project owns. Take ownership from that list only. Never infer it from the document, a naming convention, or a marker comment.

  Return structured `outcomes` — one per key — using `absent`, `equivalent`, or `divergent` (each carrying `ownership: 'tracked' | 'untracked'`), plus `obsolete-owned` (carrying `occupancy`) for an owned entry the desired set no longer names. Also return `documentPaths` (every document this change could affect, complete and non-empty) and an opaque `plan`.

  A parse or validation failure is a **value**, not a throw: `io-failed`, `parse-failed`, `validation-failed`, or `conflict`. The document must be left byte-for-byte unchanged.

  A `conflict` carries a `reason`, and each reason carries only its own facts — `interpolation` names the server and the offending value (no document: nothing has been written anywhere), `document-changed` names the drifted document, and `native-state` names the document plus your format layer's detail. None of them carries a preformatted sentence; the CLI writes the wording and escapes the value.
</ResponseField>

<ResponseField name="apply({ plan })" type="Promise<ApplyResult>" required>
  Consume the plan and perform **one atomic update per document**. Return `unchanged`, or `changed` with `changedPaths`. Every changed path MUST have been disclosed by `prepare` — the engine treats an undisclosed write as a contract violation, because it journaled preimages only for what you disclosed. If you build on the SDK scaffolding it refuses an undisclosed edit while preparing, before the plan is applicable at all.

  A handled failure must leave the document unchanged.
</ResponseField>

The plan is **opaque**. The engine stores it and hands it back; it never inspects it and never edits your tool's file itself.

### Why there is no inverse method

You are never asked to undo your own edit. Before applying a plan the engine captures the exact bytes of every document you disclosed and journals a byte-for-byte restore. Rollback therefore preserves comments, formatting, and member order without depending on adapter code being correct a second time, or on a semantic inverse reproducing a document it never parsed.

This is also why `documentPaths` must be complete and must include a file that does not exist yet: "absent" is a restorable preimage too.

### Equality decides whether anything is written

You compute equality, because you are the only component that knows your tool's schema. Compare the existing entry against **your own native rendering** of the desired declaration:

- Comments, whitespace, member ordering, and omitted-versus-empty optional collections are **not** differences.
- Anything that changes the launch or connection behavior **is** a difference.
- If you cannot *prove* equality, report `divergent`. Failing safe means an unnecessary rewrite; guessing means silently keeping a server that behaves differently from what the user approved.

An `equivalent` entry is adopted with no write at all.

### What you must preserve

You are editing a file the user owns and may already be using:

- Unrelated settings keep their semantic values.
- A server entry that is neither desired nor owned is left **completely** untouched.
- For an owned entry, native fields outside the portable model (a timeout, say) survive where your format allows.
- Use a syntax-aware edit and an atomic write. Semantic preservation is mandatory; comment and formatting preservation is best-effort and should be maximized.

Write **project-scoped configuration only**. Never create or modify a user-wide or system-wide tool file. For reference, the first-party adapters use `.mcp.json` (Claude Code), both `opencode.jsonc` and `opencode.json` as one merged configuration (OpenCode), and `.codex/config.toml` (Codex).

If your tool expands placeholders inside its own configuration values, check every authored command, argument, environment value, and URL for that syntax before writing and return a structured `conflict` when you find one. A portable declaration is literal, so writing a value your tool would substitute would launch something other than what the user approved. Claude Code (`${VAR}`) and OpenCode (`{env:...}`, `{file:...}`) both do this.

Preserve the file's encoding preamble too: if your parser cannot accept a leading byte-order mark, strip it before parsing and put it back when writing, per document. Dropping it rewrites a file the user's editor will only mark again on their next save.

Most of this is scaffolding you should not write yourself. The SDK's `prepareMcpTextPlan` and `applyMcpTextPlan` handle the interpolation guard, classification, the no-write short-circuit, document disclosure, the refusal of an edit you did not disclose, the re-read-and-compare that turns a concurrent edit into a `conflict`, and the atomic write — including for a plan that touches more than one file. You supply the tool-specific parts: which documents to read, how to parse them, how to compare an entry, and how to render an edit.

If you need to put a declaration value in front of a user yourself, import `terminalLiteral` (or `terminalCommandLine` / `terminalEnvironmentAssignment`) from `@agent-facets/adapter/terminal` — a dependency-free entry point. It is the same rendering the CLI's consent screens use: printable ASCII only, complete, and reversible, so a value cannot add a line or issue a terminal control.

<Warning>
Configuring a server is not running one. Never launch the command, connect to the URL, health-check, collect credentials, or perform OAuth. Authentication belongs to the tool, after the configuration exists.
</Warning>

## Bundle it

`facet adapter install` re-bundles your adapter into a self-contained `adapter.js`, but it needs a clean single-module entry to start from. Compile your package first  -- for example with `tsdown` (what the first-party adapters use) or `tsc`:

```sh
bunx tsdown src/index.ts
```

Point your `package.json` `exports`/`main` at the compiled entry so the CLI can resolve it.

## Install your adapter

`facet adapter install` accepts your adapter three ways:

<CodeGroup>

```sh Local directory
# Fastest while developing — installs from a local build.
facet adapter install ./my-adapter
```

```sh Git repository
# Note the git+ prefix; add #ref to pin a tag or branch.
facet adapter install git+https://github.com/you/my-adapter.git
facet adapter install git+https://github.com/you/my-adapter.git#v1.0.0
```

```sh npm package
# By package name, once you've published it.
facet adapter install my-adapter
```

</CodeGroup>

The CLI downloads the source, bundles it into `adapter.js`, verifies it exports a valid adapter, and places it in `$FACET_DIR/adapters/<name>/` (default `~/.facet`). See [`facet adapter install`](/cli/adapters/install) for every specifier format.

<Tip>
  During development, `facet adapter install ./my-adapter` picks up your latest local build immediately. Reinstall after each rebuild to test changes end-to-end.
</Tip>

## Verify it works

Confirm the adapter is registered, then install a facet to see it materialize assets:

```sh
facet adapter list          # your adapter should appear
facet add cowsay            # installs into every connected adapter, yours included
```

Check that files landed where your path helpers put them. From here, harden `buildAssetMetadata` with a real schema and flesh out the on-disk layout your tool expects.

`facet adapter list` also shows each adapter's declared adapter API and whether the CLI supports it. When a CLI release changes the supported API set, rebuild your adapter against a matching SDK release and reinstall it — the list output prints the exact reinstall command next to any incompatible entry.

Note that `supported` answers whether the adapter **loads**, not whether it can configure MCP servers. An adapter declaring `0.1`, or `0.2` with `mcpServers: false`, lists as supported and works normally — it only blocks a project that has active MCP declarations.

## Publish to npm

Installing by bare name (`facet adapter install my-adapter`) resolves through npm, and the CLI selects a release **before downloading it** by reading one required field from your published `package.json`:

```json package.json
{
  "facetAdapterApiVersion": "0.2"
}
```

Declare the adapter API version your SDK release stamps at runtime (currently `0.2`). The CLI skips releases where this field is missing, malformed, or unsupported — a release without it is never selected, and a field that disagrees with the runtime `apiVersion` stamped by `defineAdapter()` fails verification after download.

Selection is by **package version** among compatible releases; the supported API tokens are an unordered set, so `0.2` is not preferred over `0.1` — the highest satisfying release that declares *either* wins. The npm `latest` dist-tag is never consulted, so you never need to move, pin, or withhold it for compatibility.

That is what makes publishing safe in either order for consumers: a CLI supporting only `{0.1}` keeps selecting your highest `0.1` release and ignores the `0.2` one. The exception is an **exact** request (`facet adapter install my-adapter@1.4.0`), which is never substituted — it fails if that specific release is incompatible with the CLI asking.

The canonical values are exported from `@agent-facets/adapter/api-version` (`ADAPTER_API_VERSION`, `ADAPTER_API_VERSION_ASSETS_ONLY`, and `ADAPTER_API_VERSION_PACKAGE_FIELD`), so release tooling can inject the field instead of hardcoding it. That entry and `@agent-facets/adapter/terminal` are both dependency-free, so importing either one costs you nothing at runtime.

## Share it upstream

Built an adapter for a major AI coding assistant? Contributions are welcome. If your adapter targets a widely used tool, open a pull request on the [facets repository](https://github.com/agent-facets/facets) to share it upstream as a first-party adapter.

A first-party adapter is installable by name (`facet adapter install <name>`) via the CLI, so everyone using that tool benefits.
