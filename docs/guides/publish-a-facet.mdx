Publishing takes a built facet to the registry. Sign in, build, publish.

You need a facet project with a valid `facet.json` (see [Create a Facet](/guides/create-your-first-facet)) and a registry account with a <Tooltip headline="Personal access token" tip={<span>A revocable credential you mint in the web UI and use with <code>facet login</code> or <code>FACET_TOKEN</code>.</span>}>personal access token</Tooltip> from [agentfacets.io](https://agentfacets.io).

<Visibility for="agents">

> **Publishing is authenticated, and a published version is immutable.**
>
> ```sh
> export FACET_TOKEN=fct_pub_…   # or run `facet login` interactively
> facet whoami
>
> facet build
> facet publish
> ```
>
> To ship changes, bump the version (`facet modify facet --version 1.2.0`),
> rebuild, and publish again. Keep `facet build` and `facet publish` as two
> commands so a stale `dist/` never ships silently.
>
> See [`facet publish`](/cli/authoring/publish),
> [`facet build`](/cli/authoring/build), [`facet login`](/cli/login).

</Visibility>

<Visibility for="humans">

## Authenticate

```sh
facet login     # choose "Paste a personal access token"
facet whoami    # confirm the identity
```

[`facet login`](/cli/login) verifies the token against the registry before saving it, so a typo fails now rather than at publish time. [`facet whoami`](/cli/whoami) prints your username, email, and tier.

<Tip>
  In CI, skip `facet login` and set `FACET_TOKEN`. It takes precedence over the saved credentials file.
</Tip>

## Build, then publish

```sh
facet build
facet publish
```

[`facet build`](/cli/authoring/build) writes `dist/<name>-<version>.facet`. [`facet publish`](/cli/authoring/publish) validates the manifest, finds that archive, re-verifies its integrity, and uploads it under the name and version embedded in the artifact. It publishes what is in `dist/`, which is why you build first.

## When the build and source disagree

If `dist/` was built from a different `facet.json` than the one on disk, publish detects the drift and asks what to do:

- **Identity drift**: a different name or version, usually because you bumped the version without rebuilding. Build and publish current source, publish the existing artifact, or cancel.
- **Content drift**: same name and version, different content. Rebuild and publish, or publish the existing artifact unchanged.

See [drift semantics](/specification/publish#when-the-built-artifact-has-drifted-from-source).

<Warning>
  Without a terminal, both cases warn on stderr and ship the existing artifact. Run `facet build` and `facet publish` as separate commands in CI so a stale `dist/` cannot publish silently.
</Warning>

## Publish outcomes

A publish goes live, is queued for review (still a success, and it appears once approved), or is rejected because the version already exists. See [publish outcomes](/cli/authoring/publish#publish-outcomes).

## Ship a new version

A published name and version pair is immutable, so every change ships as a new version:

```sh
facet modify facet --version 1.2.0
facet build
facet publish
```

If you forget to rebuild, publish catches the identity drift and offers to build for you.

### Changing visibility

The [`private`](/specification/manifest#privacy) flag is manifest content, so changing it needs a new version:

```sh
facet modify facet --private            # or --private=false to go public
facet modify facet --version 1.3.0
facet build
facet publish
```

Omitting `private` keeps a facet public. Who can see or download a private facet is enforced by the registry. See [Private Facets](/private-facets) for scopes and access.

## Sign out

```sh
facet logout
```

[`facet logout`](/cli/logout) deletes the local credentials file. It makes no server call, so revoke tokens in the web UI.

<Warning>
  If `FACET_TOKEN` is set, it keeps authenticating after logout. Run `unset FACET_TOKEN` to sign out of the current shell.
</Warning>

`FACET_TOKEN` and `FACET_REGISTRY_URL` are documented in the [environment reference](/cli/env).
