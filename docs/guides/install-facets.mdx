Connect an adapter for your AI tool, then add the facets you want. This guide walks the loop: add, inspect, reinstall, update, and remove.

<Visibility for="agents">

> **Using facets in a project? Read the CLI's own agent instructions first.**
>
> ```sh
> facet instructions usage
> ```
>
> ```sh
> facet adapter add claude-code       # connect a tool, once per machine
> facet add viper-plans               # a bare name is a registry facet
> facet add viper-plans@1.2.3         # or pin a version
> facet install                       # after a clone, materialize from the lockfile
> facet update                        # move to newer releases
> facet remove viper-plans            # take a facet back out
> ```
>
> Add `--accept-mcp` to `add`, `install`, `update`, or `remove` when the run
> has no TTY and the project declares MCP servers. Without it the command
> fails before writing anything. Approval is per machine.
>
> `facet upgrade` is an alias of `facet update`. Neither updates the CLI
> binary; that is `facet self-update`.
>
> See [`facet add`](/cli/add), [`facet install`](/cli/install),
> [`facet update`](/cli/update), [`facet remove`](/cli/remove).

## Connect an adapter

An [adapter](/docs/learn/adapters) tells the CLI where your AI tool keeps its files and its MCP configuration. You need at least one.

```sh
facet adapter add claude-code   # or: opencode, codex
```

Run [`facet adapter add`](/cli/adapters/add) with no name for a picker. Third-party adapters install the same way from npm, a git URL, or a local path.

<Tip>
  Skip this and `facet add` opens the picker for you on first use. In CI it fails instead, so connect the adapter first.
</Tip>

## Find and add a facet

```sh
facet search viper     # browse the registry
facet add viper-plans  # add it to this project
```

[`facet add`](/cli/add) writes the entry to `facets.json` and installs it in one step. A bare name resolves to the latest registry release and is pinned to that version.

<Expandable title="Other source forms">

```sh
facet add viper-plans@1.2.3                 # exact version
facet add viper-plans@1.*                   # latest 1.x, kept as a range
facet add @acme/deploy-tools                # scoped registry facet
facet add github:owner/repo#main            # a GitHub repo at a ref
facet add ./local-facets/my-plans           # a local directory
facet add viper-plans rezi planner@2.*      # several at once
```

</Expandable>

See [`facet add`](/cli/add#source-grammar) for the full grammar and what is rejected.

## What gets written

Commit both files so teammates and CI resolve identical versions.

<CodeGroup>

```json facets.json
{
  "manifestVersion": 0.2,
  "facets": {
    "cowsay": "1.*",
    "viper-plans": "1.0.0"
  }
}
```

```json expandable facets.lock
{
  "lockfileVersion": 0.3,
  "facets": {
    "cowsay": {
      "source": { "kind": "registry", "registry": "https://api.agentfacets.io" },
      "version": "1.0.0",
      "integrity": "sha256:70fe8f9f0ba1…",
      "assets": [
        {
          "scope": "project", "type": "skill", "name": "cowsay-rules",
          "materialization": { "kind": "authored" },
          "files": [
            { "path": "skills/cowsay-rules/SKILL.md", "integrity": "sha256:11aa22…" },
            { "path": "skills/cowsay-rules/references/moods.md", "integrity": "sha256:22bb33…" }
          ]
        },
        { "scope": "project", "type": "command", "name": "cowsay",
          "materialization": { "kind": "authored" },
          "files": [{ "path": "commands/cowsay.md", "integrity": "sha256:55ee66…" }] }
      ]
    }
  }
}
```

</CodeGroup>

`facets.json` records what your project depends on and how you want its assets named. `facets.lock` records exact versions, <Tooltip headline="Integrity hash" tip="A content hash checked on every install, so you get exactly the bytes that were published." cta="How integrity works" href="/specification/integrity">integrity hashes</Tooltip>, and per-file records. The CLI owns the lockfile; never hand-edit it.

A third file, the machine-local install receipt, lives outside your project under [`$FACET_DIR`](/cli/env). It tracks what this machine wrote and holds your MCP approvals, which is why neither travels to teammates.

## Where assets land

Text assets are written into every connected adapter at project scope. With `opencode`, adding `cowsay` writes:

```
.opencode/
├── skills/cowsay-rules/SKILL.md
├── skills/cowsay-rules/references/moods.md
├── agents/cowsay.md
└── commands/cowsay.md
```

Each adapter uses its own [conventional locations](/docs/learn/adapters#where-assets-land). A skill installs and removes as one bundle, including its companion files. Files you add to a skill directory yourself are left alone. A facet's top-level `README.md` or `LICENSE` ships in the archive but is never written into your tools.

`facet remove` deletes only what your machine's receipt records installing, so a file the CLI never wrote is left in place.

## When two facets want one name

Two facets can publish a text asset with the same name. Nothing picks a winner for you, so the install pauses and asks:

```
Installation is paused: two or more facets want the same name.
1 group · 1 still to resolve · nothing has been written yet

  project skills and commands: "planning"
    ✕ unresolved   viper-plans  skill planning
    ✕ unresolved   team-tools   skill planning
```

Give each asset one outcome: **Keep** the published name, **Alias** it to a name you choose, or **Omit** it. Only one of them has to change.

Your choice is saved to `facets.json`, so it happens once:

```json facets.json
"team-tools": {
  "source": "1.*",
  "materialization": {
    "skills": { "planning": { "kind": "aliased", "as": "team-planning" } }
  }
}
```

Aliasing renames the file on disk only. The publisher's name and every integrity hash are unchanged, so an alias cannot smuggle in different content. See [Materialization](/specification/materialization).

<Warning>
  CI cannot prompt. An unresolved collision fails the run and prints the exact `facets.json` edit to make. Resolve collisions locally and commit the result.
</Warning>

## Approve MCP servers

A facet can declare [MCP servers](/docs/learn/mcp-servers). Because that configuration lets your tool run a command or open a connection, the CLI asks before writing it. One screen lists every server, the facets that want it, and the exact command, arguments, and environment values or URL. Decline is selected by default.

You are asked again only when a declaration changes. Approval is stored per machine, so a teammate approves on their own.

In CI, pre-approve the set:

```sh
facet install --accept-mcp
```

Without the flag, an unapproved declaration fails before anything is written and prints what you need to decide, including the edit that refuses one server:

```json facets.json
"mcp-tools": {
  "source": "1.*",
  "materialization": {
    "servers": { "docs": { "kind": "omitted" } }
  }
}
```

If a server name already exists in a tool's config and this project did not put it there, the same screen says so, and whether the entry matches or would be replaced.

## Reinstall after a clone

```sh
facet install
```

[`facet install`](/cli/install) materializes every declared facet at the versions in the lockfile.

<Tip>
  In CI, add `--frozen-lockfile`. It never rewrites the lockfile and fails when `facets.json` and `facets.lock` disagree. See [frozen installs](/cli/install#frozen-lockfile).
</Tip>

## Manage what is installed

```sh
facet list                     # what is declared, and what resolved
facet update                   # newest release each declared range allows
facet update --latest          # newest release, even outside those ranges
facet update --dry-run         # print the plan, change nothing
facet remove viper-plans       # take a facet out, with the files it owns
facet adapter list             # what is connected
```

[`facet update`](/cli/update) shows what is installed next to the versions it could move to. Git and local facets are listed as unsupported, since only registry facets have releases to compare. To pin instead, re-add at an exact version with `facet add viper-plans@2.0.0`.

[`facet remove`](/cli/remove) drops the facet from `facets.json`, deletes what it still owns, and rewrites the lockfile. Assets another declared facet still wants are kept, and removing a name that is not declared is a safe no-op.

Connecting an adapter later hands it everything the project already owns: the next install materializes those assets into the new tool too.
